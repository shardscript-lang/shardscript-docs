---
title: Design Best Practices
---

Writing a ShardScript native library is more than exporting two C-linkage symbols. The runtime expects a
  coherent API surface, predictable lifetime behavior, and clean interaction with the garbage collector and
  async scheduler. The practices here help you produce libraries that behave like built-in framework shards,
  compose correctly with other shards, and remain maintainable as the number of native types grows.

## Summary

  A well-designed native library exposes one logical API surface per shared library, follows existing
  framework naming conventions, uses the registration helpers correctly, and respects the runtime&apos;s
  memory and threading model. This article explains how to structure a library, avoid common lifetime
  mistakes, register symbols cleanly, produce async primitives, and declare dependencies so the loader can
  enforce load order.

## What problem it solves

  Native libraries sit at the boundary between C++ and managed ShardScript code. Without a consistent design,
  you can end up with:

  - **Scattered or duplicated APIs** — one physical file that registers several unrelated namespaces, or several build outputs that claim the same namespace.
  - **Use-after-collect crashes** — an object is passed to a thread-pool callback and collected before the callback runs.
  - **Leaked native handles** — a type wraps a file descriptor, socket, or OS handle but never releases it when the managed object disappears.
  - **Fragile cross-library lookups** — static pointers are initialized before the dependency has registered its symbols, producing null pointers at runtime.
  - **Inconsistent async behavior** — callbacks complete tasks on the wrong thread or re-implement state machines that the runtime already provides.

  The guidelines below prevent these problems by matching the conventions already used in the framework
  shards.

## How it works

  A native library is any shared library (a `.dll` on Windows, a
  `.so` on Linux, or a `.dylib` on macOS) that exports exactly
  two C-linkage symbols: `ShardLib_GetMetadata` and
  `ShardLib_EntryPoint`. The library can be built from one C++ source file or many,
  and it can live inside `ShardScript.Framework` or in a completely separate project.
  It links against the ShardScript runtime shared library and includes headers from
  `ShardScript/include`.

  Inside `SHARDLIB_ENTRYPOINT` you register namespaces, types, methods, properties,
  and operators into the compiler&apos;s semantic model. The runtime then invokes your callbacks whenever
  ShardScript code calls the registered members. Every design decision below is about keeping that contract
  predictable.

## Key ideas

## One logical library per shared library

  Keep one coherent API surface per shared-library output. In the framework this usually means one
  `.shard.cpp` file per shared library, but the rule is broader: a single library
  should own one namespace (or a small family of closely related namespaces) and one responsibility. Do not
  register unrelated APIs in the same shared library, and do not split a single logical API across multiple
  shared libraries unless the dependencies genuinely justify it.

// mynetworking.shard.cpp
```cpp
#include <ShardScript.hpp>

using namespace shard;

SHARDLIB_GETMETADATA
{
    lib.Name        = L"shard.mynetworking";
    lib.Description = L"TCP and UDP networking primitives";
    lib.Version     = L"0.1.0";
}

SHARDLIB_ENTRYPOINT
{
    SymbolBuilder<NamespaceSymbol> net(context, L"net");

    net.AddClass(L"Socket", ACS_PUBLIC, LINK_INSTANCE, [](SymbolBuilder<ClassSymbol> cls)
    {
        cls.AddMethod(L"Connect", TYPE_VOID, LINK_INSTANCE)
            .AddParameter(L"host", TYPE_STRING)
            .AddParameter(L"port", TYPE_INT)
            .SetCallback(&Socket_Connect);
    });
}
```

## Mirror .NET-style APIs

  When you wrap OS services or design new system APIs, prefer names and shapes that match .NET class
  libraries. This makes the framework feel consistent and lowers the learning curve for developers who know
  other managed environments.

  - Use namespaces such as `net`, `io`,  `process`, `text`, and `collections`.
  - Name stream types `FileStream`, `MemoryStream`,  `StreamReader`, and `StreamWriter`.
  - Use `Dispose()` for deterministic cleanup and implement  `IDisposable`.
  - Prefer asynchronous methods that return `async.Task` or  `async.ValueTask<T>` with an `Async` suffix.

<Info>
Consistency matters more than literal .NET compatibility. Choose names that fit the existing framework
  shards so that code written against one library transfers naturally to the next.
</Info>

## Implement IDisposable for native handles

  Any type that owns an unmanaged handle, pointer, file descriptor, or other external resource should
  implement `IDisposable`. Call `.Implements(TRAIT_DISPOSABLE)`
  on the class and provide a `Dispose` method that releases the native resource. Also
  store the handle in a private `nint` field so the GC does not try to interpret it as
  a managed reference.

// streams.shard.cpp
```cpp
#include <ShardScript.hpp>

using namespace shard;

static FieldSymbol* FileStream_handleField = nullptr;

static ObjectInstance* FileStream_Dispose(const CallState& context)
{
    ObjectInstance* self = context.Args[0];
    ObjectInstance* handleObj = self->GetField(FileStream_handleField->SlotIndex);

    if (handleObj != nullptr && handleObj != GarbageCollector::NullInstance)
    {
        void* handle = handleObj->AsNint();

        if (handle != nullptr)
        {
            // Release the OS handle and clear the slot so Dispose is idempotent.
            CloseNativeHandle(handle);
            self->SetField(FileStream_handleField->SlotIndex, GarbageCollector::NullInstance);
        }
    }

    return nullptr;
}

SHARDLIB_ENTRYPOINT
{
    SymbolBuilder<NamespaceSymbol> io(context, L"io");

    io.AddClass(L"FileStream", ACS_PUBLIC, LINK_INSTANCE, [](SymbolBuilder<ClassSymbol> cls)
    {
        FileStream_handleField = cls.AddField(L"_handle", TYPE_NINT, LINK_INSTANCE, ACS_PRIVATE);

        cls.Implements(TRAIT_DISPOSABLE);

        cls.AddMethod(L"Dispose", TYPE_VOID, LINK_INSTANCE)
            .SetCallback(&FileStream_Dispose);
    });
}
```

## Use ObjectRef to pin objects across async boundaries

  When an `ObjectInstance*` escapes the synchronous callback boundary, for example into
  a thread-pool worker or a libuv handle, the garbage collector may collect it before the async work finishes.
  Use `ObjectRef` to keep the object alive. The reference is released when the
  `ObjectRef` goes out of scope or is assigned a new value.

// socket.shard.cpp
```cpp
#include <ShardScript.hpp>
#include <shard/runtime/NativeAsync.hpp>

using namespace shard;

static ObjectInstance* Socket_ReadAsync(const CallState& context) noexcept
{
    ObjectInstance* socket = context.Args[0];

    return shard::DoValueTask<std::int64_t>(context, [socket](shard::AsyncValueScope<std::int64_t> async)
    {
        ObjectRef pinnedSocket(socket);

        async.RunOnThreadPool([async, pinnedSocket]() mutable
        {
            ObjectInstance* self = pinnedSocket.Get();

            if (self == nullptr || self == GarbageCollector::NullInstance)
            {
                async.Complete(0);
                return;
            }

            // Read from the native socket while the managed object stays pinned.
            std::int64_t bytesRead = ReadFromNativeSocket(self);
            async.Complete(bytesRead);
        });
    });
}
```

<Warning>
Do not store a raw `ObjectInstance*` in a lambda or native handle and use it later
  without an `ObjectRef`. The object may have been moved or collected.
</Warning>

## Avoid global constructors that touch ShardScript symbols

  All symbol registration must happen inside `SHARDLIB_ENTRYPOINT`. Do not rely on
  global C++ constructors to register types, cache symbol pointers, or initialize field layouts. Load order
  between libraries is not guaranteed, and global constructors run before the runtime is ready to accept
  registrations.

// mylib.shard.cpp
```cpp
#include <ShardScript.hpp>

using namespace shard;

// Safe: these are plain pointers initialized to null and assigned inside the entry point.
static FieldSymbol* g_bufferField = nullptr;
static TypeSymbol*  g_otherType   = nullptr;

static void EnsureOtherType(SymbolTable* table)
{
    if (g_otherType != nullptr)
    {
        return;
    }

    g_otherType = SemanticModel::FindTypeByName(table, L"othernamespace.OtherType");
}

SHARDLIB_ENTRYPOINT
{
    SymbolFactory factory(context.GetSemanticModel().Table.get());
    SymbolBuilder<NamespaceSymbol> myLib(context, L"mylib");

    myLib.AddClass(L"Buffer", ACS_PUBLIC, LINK_INSTANCE, [](SymbolBuilder<ClassSymbol> cls)
    {
        ArrayTypeSymbol* byteArray = factory.Array(TYPE_BYTE);
        g_bufferField = cls.AddField(L"_data", byteArray, LINK_INSTANCE, ACS_PRIVATE);
    });
}
```

## Use SymbolFactory for arrays and generics

  Do not construct array or generic type symbols manually. Use `SymbolFactory` so the
  semantic model receives correctly linked type arguments. This is especially important when registering
  generic classes or fields whose type involves a type parameter.

// collections.shard.cpp
```cpp
#include <ShardScript.hpp>
#include <shard/semantic/SymbolFactory.hpp>

using namespace shard;

SHARDLIB_ENTRYPOINT
{
    SymbolFactory factory(context.GetSemanticModel().Table.get());

    SymbolBuilder<NamespaceSymbol> collections(context, L"collections");

    collections.AddClass(L"List", ACS_PUBLIC, LINK_INSTANCE, [](SymbolBuilder<ClassSymbol> cls)
    {
        TypeParameterSymbol* T = cls.AddTypeParameter(L"T").Get();

        // Use the factory to build the array-of-T field type.
        ArrayTypeSymbol* arrayOfT = factory.Array(T);
        cls.AddField(L"_items", arrayOfT, LINK_INSTANCE, ACS_PRIVATE);

        cls.AddMethod(L"Add", TYPE_VOID, LINK_INSTANCE)
            .AddParameter(L"value", T)
            .SetCallback(&List_Add);
    });
}
```

## Prefer DoAsync and DoValueTask

  Use `shard::DoAsync` and `shard::DoValueTask<T>` instead
  of manually allocating task objects and manipulating libuv handles. The helpers ensure the task is created
  on the correct event-loop thread, transition states safely, and marshal continuations properly.

// sensors.shard.cpp
```cpp
#include <ShardScript.hpp>
#include <shard/runtime/NativeAsync.hpp>

using namespace shard;

static ObjectInstance* DelayMilliseconds(const CallState& context) noexcept
{
    std::int64_t milliseconds = context.Args[0]->AsInteger();

    return shard::DoAsync(context, [milliseconds](shard::AsyncScope async)
    {
        async.Delay(static_cast<std::uint32_t>(milliseconds), [async]() mutable
        {
            async.Complete();
        });
    });
}

static ObjectInstance* ReadTemperatureAsync(const CallState& context) noexcept
{
    return shard::DoValueTask<double>(context, [](shard::AsyncValueScope<double> async)
    {
        async.RunOnThreadPool([async]() mutable
        {
            // Simulate a sensor read on a worker thread.
            double temperature = ReadSensor();
            async.Complete(temperature);
        });
    });
}
```

<Info>
Fall back to manual task allocation only when you need features the helpers do not provide, such as custom
  cancellation-token integration or explicit control over continuation scheduling.
</Info>

## Document dependencies in metadata

  If your library uses symbols from another shard, declare the dependency in
  `SHARDLIB_GETMETADATA`. The runtime loader uses this list to enforce load order and
  to fail early with a clear message when a required shard is missing.

## Avoid conditional symbol registration

  It is technically possible to register namespaces, classes, methods, or other members only when a
  runtime condition is met — for example, when another library is present, a file exists, or an
  environment variable is set. The registration APIs do not prevent this, and there are legitimate
  edge cases where it can be useful. However, it is strongly recommended to avoid conditional
  registration in production libraries. A symbol surface that changes based on external state creates
  uncertainty for callers, makes static analysis and tooling unreliable, and leaves gaps in any
  documentation or IDE support generated from the library. Prefer a stable, always-registered API and
  expose runtime availability through explicit properties or factory methods that callers can check
  from ShardScript code.

// filesystem.shard.cpp
```cpp
SHARDLIB_GETMETADATA
{
    lib.Name        = L"shard.filesystem";
    lib.Description = L"File and directory APIs";
    lib.Version     = L"0.2.0";

    static const shard::ShardLibDependencyInfo deps[] =
    {
        { L"shard.streams",   L"0.1.0" },
        { L"shard.collections", L"^0.3.0" }
    };

    lib.Dependencies = deps;
    lib.DependenciesLength = sizeof(deps) / sizeof(deps[0]);
}
```

  Even with declared dependencies, look up cross-library symbols lazily inside
  `EnsureSymbols` helpers rather than caching pointers during static initialization.
  Load order between dependencies is guaranteed, but individual symbols inside those libraries should still be
  resolved on demand.

## Additional conventions

  - **Expose constants as static properties** — use  `AddProperty` with a getter callback so values are read-only from ShardScript.
  - **Throw std::runtime_error for expected failures** — the runtime converts thrown exceptions into ShardScript exceptions with the provided message.
  - **Use explicit accessibility** — keep helper fields private and public only the types and members that callers need.
  - **Match linking mode to call site** — register static members with `LINK_STATIC` and instance members with  `LINK_INSTANCE`.

## When to use

  - You are writing a new framework shard or wrapping an external C/C++ library for ShardScript consumption.
  - The library manages unmanaged resources, performs asynchronous I/O, or depends on symbols from other native libraries.
  - You want the library to feel like a built-in part of the ShardScript standard library.

## When not to use

  - The code is pure ShardScript business logic. Keep it in ordinary  `.shard` source files so you retain debugging and hot-reload support.
  - You only need to call a few raw C functions from a one-off shared library. Use  `interop.NativeLibrary` instead of authoring a full native library.
  - You are tempted to register many unrelated namespaces in a single shared library. Split them into separate libraries with their own dependencies and metadata.
