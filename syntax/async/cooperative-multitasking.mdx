---
title: Cooperative Multitasking
---

ShardScript programs are **single-threaded and cooperative**. Instead of spawning one OS thread per asynchronous operation, the runtime multiplexes every timer, I/O request, and background offload through one `libuv` event loop. An `async` method runs only while it has work to do; when it reaches an `await`, it yields control back to the loop so other tasks can run. This model gives the appearance of concurrency without locks, race conditions, or preemptive context switches.

## What it is

  At the center of asynchronous execution is the `EventLoop` class owned by each `ApplicationDomain`. It wraps a single `uv_loop_t` from libuv and is shared by every virtual machine in that domain. The loop keeps track of active handles such as timers (`uv_timer_t`) and async send handles (`uv_async_t`), invoking their callbacks when the underlying OS signals readiness.

| Concept | Runtime representation | Role |
| --- | --- | ---
| `EventLoop` | uv_loop_t wrapper | Schedules all async work on a single thread. |
| `Task` | Object instance with state, continuation, and exception fields | Represents an operation that completes or faults in the future. |
| `IAwaiter / IAwaitable` | Interface contracts | Allow any type to participate in await. |
| `NativeContinuation` | Internal IAsyncState implementation | Bridges libuv callbacks back into VM bytecode. |
| `RootTask` | Reference-counted list in EventLoop | Keeps pending Task objects alive across suspensions. |

  When an async method is invoked, the compiler has already rewritten it into a state machine with a `MoveNext` method. The first `MoveNext` call runs synchronously until the first `await`. At that point the method registers its own state machine as the awaited task&apos;s continuation and returns. Later, when the libuv callback completes the task, the runtime calls `ResumeContinuation`, which invokes `MoveNext` again to continue exactly where execution left off.

## When to use it

  - **I/O-bound work.** HTTP requests, socket reads, file system operations, and timers spend most of their time waiting. Cooperative multitasking lets one thread juggle hundreds of pending operations.
  - **Many lightweight concurrent operations.** Spawning a thread per counter, delay, or connection is expensive; scheduling callbacks on a shared loop is cheap.
  - **Scenarios that need simple sequencing.** Because awaits are expressed directly in the source, reading and writing async code follows the same top-to-bottom order as synchronous code.
  - **Heavy CPU work.** Long-running computations must be offloaded with `RunOnThreadPool` so they do not starve the event loop.

## Fire-and-forget vs blocking wait

  ShardScript offers two ways to relate a synchronous caller to an async operation:

| Style | Syntax | Behavior | Use when |
| --- | --- | --- | ---
| Blocking wait | `Task.Wait(task)` | Pumps the event loop until the task completes, then returns (or rethrows a fault). | The caller needs the result or completion before continuing. |
| Fire-and-forget | `Background();` or `Task.Shoot(task);` | Starts the operation and lets the loop drive it to completion independently. | The caller does not depend on the outcome. |

  `Task.Wait` is the typical bridge from synchronous `Main` into async code. It is implemented as a tight loop that calls `EventLoop.RunOnce()` until the task leaves the `PENDING` state. While the call blocks its caller, the loop underneath continues to drain timers and I/O, so other tasks still make progress.

<Info>
A pending task is **rooted** by the event loop while it is suspended. Rooting keeps the task alive even if no ShardScript variable references it, which is why fire-and-forget calls do not disappear mid-flight.
</Info>

## Remarks

  **Single-threaded means no preemptive races.** Because only one piece of VM code runs at a time, two async methods cannot mutate the same object simultaneously. The only way to interleave is through an explicit `await`, so reasoning about shared state is straightforward.

  **CPU work starves the loop.** If an async method performs a long computation without awaiting, no timer or I/O callback can run. Native shards solve this by calling `AsyncScope::RunOnThreadPool`, which runs the work on a background `std::thread` and posts completion through a `uv_async_t` handle. The continuation always runs back on the loop thread, so VM state remains safe to touch.

  **Exceptions propagate through the task.** If an async method throws before its first await, the exception is captured in the returned `Task`. If it throws after an await, the state machine captures it into the task&apos;s exception field. `Task.Wait` rethrows the captured exception into the caller, which is why wrapping async calls in `try/catch` works as expected.

  **Do not call `Task.Wait` inside an async method.** Because the loop is single-threaded, blocking the loop waiting for a task prevents the very callback that would complete that task. This produces a deadlock. Inside async code, use `await` instead.

<Warning title="Composition helpers not yet implemented">
Helpers such as `Task.WhenAll`, `Task.WhenAny`, and `Task.ContinueWith` are not available today. To wait for multiple operations, store each `Task` in a variable and call `Task.Wait` on them in the order you need, or await them sequentially inside another `async` method.
</Warning>

## Examples

  **Interleaved timers.** Three counters start together. The first await in each returns control to the loop, so the shortest delay finishes first even though the methods were called in A-B-C order.

// interleaved_counters.shard
```csharp
using stdio;
using async;

namespace demo;

async func CounterA() -> Task
{
    println("A: 1");
    await Task.Delay(500);
    println("A: 2");
    await Task.Delay(500);
    println("A: 3");
}

async func CounterB() -> Task
{
    println("B: 1");
    await Task.Delay(800);
    println("B: 2");
    await Task.Delay(800);
    println("B: 3");
}

async func CounterC() -> Task
{
    println("C: 1");
    await Task.Delay(300);
    println("C: 2");
    await Task.Delay(300);
    println("C: 3");
}

public static func Main() -> void
{
    t1: Task = CounterA();
    t2: Task = CounterB();
    t3: Task = CounterC();

    Task.Wait(t1);
    Task.Wait(t2);
    Task.Wait(t3);

    println("All counters finished");
}
```

  **Blocking wait from synchronous code.** This is the normal entry pattern: start the async operation, then pump the loop until it finishes.

// blocking_wait.shard
```csharp
using stdio;
using async;

namespace demo;

async func DelayedHello() -> Task
{
    println("before");
    await Task.Delay(100);
    println("after");
}

public static func Main() -> void
{
    task: Task = DelayedHello();
    Task.Wait(task);
    println("done");
}
```

  **Fire-and-forget.** The background task starts without blocking `Main`. The runtime keeps it alive until the delay fires and the method completes.

// fire_and_forget.shard
```csharp
using stdio;
using async;

namespace demo;

public class Program
{
    public static async func Background() -> Task
    {
        println("background start");
        await Task.Delay(100);
        println("background end");
    }

    public static func Main() -> void
    {
        // Start the operation and intentionally do not wait.
        Background();
        println("main end");
    }
}
```

<Info>
To make fire-and-forget intent explicit, call `Task.Shoot(task)`. `Task.Shoot` marks the task as detached and is useful when a linter or reader needs to know the result is intentionally ignored.
</Info>

  **Custom awaitable.** Any type implementing `IAwaitable` and returning an `IAwaiter` can be awaited. This is how native shards surface libuv handles to ShardScript code.

// custom_awaitable.shard
```csharp
using stdio;
using async;

namespace demo;

public class MyAwaiter : IAwaiter
{
    public func IsCompleted() -> bool
    {
        return true;
    }

    public func OnCompleted(continuation: IAsyncState) -> void


    public func GetResult() -> int
    {
        return 123;
    }
}

public class MyAwaitable : IAwaitable
{
    public func GetAwaiter() -> MyAwaiter
    {
        return new MyAwaiter();
    }
}

public class Program
{
    public static async func Test() -> Task
    {
        a: MyAwaitable = new MyAwaitable();
        x: int = await a;
        println(x);
    }

    public static func Main() -> void
    {
        Task.Wait(Test());
    }
}
```

  **Offloading CPU-bound work from a native shard.** The `RunOnThreadPool` helper is not exposed directly to ShardScript; it is the pattern native libraries use when they need to perform blocking or CPU-heavy work without freezing the loop. The work lambda runs on a background thread, and the completion lambda runs on the loop thread through a `uv_async_t` handle.

// thread_pool_offload.cpp
```cpp
#include <shard/runtime/NativeAsync.hpp>

// Inside a native shard callback.
static ObjectInstance* HeavySumAsync(const CallState& context) noexcept
{
    std::int64_t count = context.Args[0]->AsInteger();

    return shard::DoAsync(context, [count](shard::AsyncScope async)
    {
        async.RunOnThreadPool(
            [count]()
            {
                // This executes on a background std::thread.
                std::int64_t sum = 0;
                for (std::int64_t i = 0; i < count; i = i + 1)
                {
                    sum = sum + i;
                }
            },
            [async]() mutable
            {
                // This continuation runs back on the libuv loop thread.
                async.Complete();
            }
        );
    });
}
```

  **Common mistakes.**

  - **Blocking the loop.** Avoid synchronous sleeps or long loops inside async methods. Use `Task.Delay` for delays and `RunOnThreadPool` for heavy work.
  - **Waiting inside async code.** `Task.Wait` inside an `async func` deadlocks the single-threaded loop. Always `await` instead.
  - **Forgetting the task lifetime.** A task is rooted while pending, but the root is released when it completes. If you need the result later, keep a variable referencing it so the GC does not collect the completed object before you read it.
  - **Awaiting outside async.** `await` is only valid inside an `async func` or async lambda. Using it in an ordinary method is a compile-time error.
